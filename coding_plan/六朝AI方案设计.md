# 六朝何事 — AI Agent 方案设计

> 创建: 2026-07-31 | 整合本会话中关于六朝 AI 设计的全部讨论

## 一、设计目标与约束

### 1.1 三层目标

| 层 | 职责 | 输入 | 输出 |
|----|------|------|------|
| **L1: 对局 Agent** | 在游戏中做决策 | GameState | 选定的 Action |
| **L2: 赛后分析** | 总结本局经验、识别关键决策点 | GameLog + L1 决策记录 | 经验报告 |
| **L3: 规则建议** | 跨局分析，提出平衡性/规则修改建议 | 多局 L2 报告 | 规则修改提案 |

本文聚焦于 **L1（对局 Agent）** 的方案设计，L2/L3 依赖 L1 的输出做分析。

### 1.2 六朝的关键复杂度

| 维度 | 数值/特征 | 对 AI 的影响 |
|------|----------|-------------|
| 玩家结构 | 4 人不完全信息（1 北方 + 3 东晋） | 非对称、非零和、合作+竞争 |
| 卡牌 | 177 张，含角色/幕僚/策略/事件 | 分支因子大（每步 15-30 可选行动） |
| 区域 | 12 个区域，区控 VP + 文化传播 | 空间规划维度 |
| 文化轨 | 3 条（儒学/玄学/佛学） | 多维排名竞争 |
| DBG | 策略牌加入阵营牌库 → 朝堂区 → 激活 | 延迟回报链 |
| 每局行动数 | ~200 步 | 搜索到终局不可行 |
| 隐藏信息 | 对手手牌、公共牌库顺序、秘密目标 | 需要 determinization |

### 1.3 引擎已有基础

- **GameAgent 接口**（`engine/ai/interface.py`）：`decide_action()`, `make_choice()`, `select_target()` 等
- **HeuristicAI**（`engine/ai/heuristic_ai.py`）：手工规则打分，可作为 baseline 和 rollout 策略
- **DummyAI**（`engine/ai/dummy_ai.py`）：加权随机，可作为随机 baseline
- **SnapshotViewport**（`engine/viewport/snapshot.py`）：冻结的 JSON 化游戏状态，已处理可见性过滤
- **GameLogger**（`engine/engine/game_logger.py`）：结构化 JSON 日志 + 文本日志

## 二、游戏 AI Agent 与通用 Agent 的核心差异

在讨论具体方案之前，先明确一个前提：游戏 AI Agent 和通用 Agent（编码助手、客服机器人、自动化工作流等）有本质差异。这些差异决定了哪些技术路线可行、哪些不可行。

### 2.1 差异一：前向模型 — 存在 vs 不存在

这是**最根本的差异**，其他所有差异几乎都由此派生。

```
通用 Agent:
  行动: "发送这封邮件" → 后果: ?
  行动: "部署这个配置" → 后果: ?
  → 无法模拟。环境是真实世界，行动不可逆。
  → 规划只能靠推理（"如果...那么..."），不能靠搜索。

游戏 AI Agent:
  行动: "CourtAction(士卒)" → 后果: +3 军力，牌进入 played 区
  行动: "March(寿春)"     → 后果: 部队推进 1 格，消耗 3 军力
  → 完美前向模型。状态转移函数 f(S, A) = S' 完全已知。
  → 规划可以用搜索（"我先试一下这步，看看 5 步后局面如何"）。
```

**这就是为什么 MCTS、Beam Search 这些搜索算法在游戏 AI 中是核心工具，在通用 Agent 中根本不存在。** `GameEngine.apply_action()` 就是一个免费的"时光机"——通用 Agent 永远没有。

### 2.2 差异二：目标函数 — 内生 vs 外赋

```
通用 Agent:
  用户: "帮我重构这个模块"
  Agent: 重构到什么程度算好？可读性？性能？可测试性？
  → 目标来自用户，模糊、多维度、不可形式化
  → "成功"是一个价值判断，不是一个数学结果

游戏 AI Agent:
  游戏规则: "终局时 VP 最高者胜"
  Agent: 最大化 VP
  → 目标来自游戏本身，精确、标量化、完全形式化
  → "成功"是一个数学结果（max VP），不需要任何人来定义
```

通用 Agent 的困境是"我不知道什么算好"。游戏 Agent 的优势是"游戏规则已经精确地定义了什么叫好"——VP 就是好，赢就是好。

**但这同时是陷阱**：Goodman 论文的核心发现——Dominion 中 VP 是欺骗性信号，"现在不拿 VP 反而最终赢"。游戏的目标函数是精确的，但**作为中间评估的代理（proxy）可能是误导性的**。通用 Agent 没有这个陷阱（因为它根本没有精确目标），但也没有这个优势。

### 2.3 差异三：状态空间 — 有限形式化 vs 开放自然语言

```
通用 Agent:
  状态: "代码库有 200 个文件，用户说这段逻辑有问题，但没说清楚..."
  → 状态是开放的、模糊的、部分可观察的
  → 用自然语言描述状态本身就是一次信息压缩/扭曲
  → LLM 的价值: 自然语言是编码模糊状态的最佳媒介

游戏 AI Agent:
  状态: GameState { vp: 45, military: 3, hand: [Card(谢玄), ...], ... }
  → 状态是封闭的、精确的、形式化定义的
  → 状态表示是无损的（GameState 包含了全部可知信息）
  → LLM 的代价: 自然语言是编码精确状态的低效媒介
```

这解释了为什么 StateEncoder（GameState → Markdown）是六朝 AI 的 P0 任务。它把"精确但 LLM 读不懂"的状态翻译成"LLM 能推理但会丢信息"的状态——这个翻译的质量决定了整个 LLM-Hybrid 的上限。

### 2.4 为什么会存在这些差异？

**一句话：游戏是设计出来的封闭形式系统，现实世界不是。**

- 游戏有**作者**（game designer），作者定义了完整的规则、边界和胜利条件。这个封闭性是搜索算法的前提。
- 现实世界没有作者，规则是隐含的、不完整的、随时变化的。LLM 之所以在通用 Agent 中不可替代，是因为它是对"非形式化世界"建模的最有效工具。
- 通用 Agent 面临的是**开放性**问题（open-ended），游戏 Agent 面临的是**复杂性**问题（combinatorial）——两者都需要智能，但需要的类型不同。

### 2.5 对六朝设计的实践含义

```
通用 Agent 的武器          游戏 AI 的武器
─────────────────────    ─────────────────────
LLM 推理（自然语言）       前向模型（搜索）
模糊目标处理              精确目标优化
开放状态理解              形式化状态利用
常识 + 背景知识            规则完备性
工具调用                  模拟/自对弈
─────────────────────    ─────────────────────
         ↓                     ↓
         └─────────┬───────────┘
                   ↓
        六朝 LLM-Hybrid 的设计空间:
        
        LLM 负责:                搜索负责:
        - 战略方向                - 战术组合
        - 对手推理 (ToM)          - 资源计算
        - 跨回合规划              - 短视界最优序列
        - 异常判断                - 朝堂选牌组合链
```

## 三、六朝 AI 决策问题全景分析

六朝一局约 **200+ 次决策**，分布在多种截然不同的决策类型中。在讨论解决方案之前，必须先理清"要决策什么"。

### 3.1 按时间线展开

#### 阶段 0：Setup（开局前，~8 次决策）

| 决策 | 选项数 | 难度 | 特征 |
|------|--------|------|------|
| **选择角色** | ~10 位英雄 | ⭐⭐⭐ | 一局只做一次，决定整局策略方向 |
| **选择初始手牌** | 从分发牌中选 N 张保留 | ⭐⭐ | 影响前 2-3 回合的节奏 |
| **选择公开策略牌** | 多选 | ⭐⭐ | 影响全局可用的公共行动 |

**为什么难**：信息最少（不知道对手选谁、不知道牌库顺序）、影响最深远。

#### 阶段 1：Action Loop（每回合，~180 次决策）

这是密度的核心。玩家在自己的回合中反复从 5 类行动中选择一个执行，直到主动结束回合。

```
可用行动池（~15-30 个/步）:
├─ Quick Actions（无限次使用，个别有次数限制）
│  ├─ 进军 March        — 消耗军力，推进部队
│  ├─ 占领 Occupy       — 部署部队，控制区域
│  ├─ 驻防 Fortify      — 1次/回合，加强防御
│  ├─ 摸牌 Draw         — 1次/回合，花2军力摸1张
│  └─ 征募 Recruit      — 弃1牌→+1军力
│
├─ Hand Actions（1次/回合默认）
│  └─ 打出手牌 — 策略牌/幕僚牌/事件牌
│
├─ Court Actions（1次/回合默认）
│  └─ 激活朝堂策略牌 — 即时效果
│
├─ Public Actions（占用 Hand Action 槽位）
│  └─ 使用公开策略牌
│
├─ Activate Actions（每张角色/幕僚牌1次/回合）
│  └─ 激活角色/幕僚主动技能
│
└─ EndTurn — 结束行动循环
```

#### 阶段 2：被动响应（对手回合中，不定次数）

| 决策 | 触发条件 | 特征 |
|------|---------|------|
| **选择弃牌** | 被对手效果要求弃牌 | 多选（"弃哪张？"） |
| **选择目标** | 效果要求指定目标（区域/玩家/卡牌） | 单选 |
| **选择选项** | 效果给出多选项（"A 或 B"） | 二选一或多选一 |
| **僭越宣言** | 满足僭越条件时 | 二选一（僭/不僭），高影响力 |

#### 阶段 3：特殊决策点（~3-5 次/局）

| 决策 | 触发时机 | 为什么特殊 |
|------|---------|-----------|
| **僭越决策** | 威望超过对手时 | 离散、高影响力、不可逆 |
| **终局触发** | 部队耗尽时 | 提前结束 vs 继续，影响所有人 |
| **皇帝骰子** | 准备阶段 | 消耗军力达成君主任务 |
| **结算阶段朝堂分配** | 轮次结束 | 未激活朝堂牌的 army+VP 自动结算 |

### 3.2 按决策特性分类 — 五类决策

从 AI 设计的角度，更有效的分类是按**决策的内在特性**来分：

#### 类型 A：资源分配型（"我有 X 个资源，怎么花"）

```
特征:
  - 有明确的兑换率可参考（1 军力 ≈ 1.5 VP ≈ 1 张牌的成本）
  - 通常可组合（先做 A 再做 B vs 先做 B 再做 A）
  - 部分可逆（资源可再生，下回合又有）
  - 有短期/长期 trade-off

代表决策:
  - 征募 (弃牌→军力): 弃哪张？值不值得？
  - 摸牌 (军力→牌): 2 军力换 1 张牌，边际价值递减
  - 打出手牌: 现在打 vs. 等下回合再打？
  - 朝堂选牌: 激活哪个？

AI 视角:
  → 适合搜索算法（Beam Search、MCTS）
  → 形式化程度高，可精确计算期望值
  → 难点在组合链的发现（"弃这张 → +1军力 → 进军 → 占领"）
```

#### 类型 B：空间规划型（"往哪走，占哪块地"）

```
特征:
  - 12 个区域构成地图网络（非均匀价值、邻接关系）
  - 区域控制涉及三方博弈（东晋 3 家 + 北方 1 家）
  - 地理约束（只能进军邻接区域、需要补给线）
  - 文化传播叠加在区域控制之上

代表决策:
  - 进军方向: 寿春？襄阳？关中？
  - 占领时机: 现在占 vs. 等部队积累更多？
  - 驻防选择: 哪个区域最可能被攻击？
  - 文化传播地点: 儒学到荆州？玄学到扬州？

AI 视角:
  → 适合战略层 LLM 推理（"拓跋珪在河北，我先守淮南"）
  → 不适合纯搜索（地图空间太大，每一步 12 个方向）
  → 对手的回应是核心变量（"我进军襄阳，王导会不会跟我抢？"）
```

#### 类型 C：DBG 构筑型（"往牌库里塞什么，抽到什么打什么"）

```
特征:
  - 延迟回报: 策略牌加入阵营牌库 → N 回合后才在朝堂区出现
  - 信息不完全: 不知道牌库当前顺序
  - 牌组质量是长期竞争力的核心（Goodman 论文关键教训）
  - 涉及两阶段: (1) 打策略牌入库 (2) 激活朝堂牌

代表决策:
  - 打策略牌: 把什么牌加入阵营牌库顶部？
  - 朝堂选牌: 现在激活 vs. 等更好的牌出现？
  - 弃牌（手牌限制）: 保留什么？
  - 摸牌（快速行动）: 值不值得花 2 军力？

AI 视角:
  → 战略层 LLM（理解"现在加牌，3 回合后爆发"）
  → 朝堂选牌用搜索（10 张已知，短视界）
  → 最大的陷阱来自 Goodman 论文: VP 是欺骗性信号
```

#### 类型 D：社交博弈型（"对手在想什么，我要怎么对他"）

```
特征:
  - 涉及 Theory of Mind（推测对手意图和手牌）
  - 二选一的高影响力决策
  - 信号传递（我的行动向对手传递了什么信息？）
  - 非对称关系（东晋 3 家之间有合作有竞争）

代表决策:
  - 僭越: 威望够了要不要僭？
    考量: 对手有没有反制牌？盟友会不会趁机背刺？
  - 终局触发: 要不要耗尽部队提前结束？
    考量: 现在的排名在终局对我有利吗？
  - 目标选择: 攻击谁？帮谁？（多目标效果中）
  - 皇帝骰子: 完成哪个君主任务？（影响东晋排名）

AI 视角:
  → LLM 的绝对优势领域（Theory of Mind、情境化推理）
  → MCTS 最弱的领域（同质化对手假设、"策略融合"）
  → 对六朝尤其关键: 东晋三家之间的"合作竞争"关系
```

#### 类型 E：反应型（"被迫回应，选项有限"）

```
特征:
  - 由对手行动或游戏事件触发
  - 选项少（通常 2-4 个）
  - 通常是被动的、防御性的
  - 信息量小（不知道对手为什么针对你）

代表决策:
  - 被要求弃牌: 弃哪张？（需要快速判断每张牌的价值）
  - 被要求选择: 给对手什么资源？
  - 结算选择: 获得 A 还是 B？

AI 视角:
  → 适合简单规则/启发式（选项少、判断标准明确）
  → 不需要复杂搜索或 LLM
  → 关键是判断时机（"现在还早，这张牌后面有用"）
```

### 3.3 决策矩阵总结

```
类型           频率/局   分支   视界     信息完备度   对手互动   推荐方案
──────────────────────────────────────────────────────────────────
A 资源分配     ~100     15-30   短(1-3步)   高 (已知资源)   低       Beam Search
B 空间规划     ~30      12      中(1-5步)   中 (可见地图)   高       LLM 战略
C DBG 构筑     ~20      4-10    长(2-5回合)  低 (未知牌序)  中       LLM 战略
D 社交博弈     ~5       2-4     长(终局影响) 极低 (未知意图) 极高    LLM 直接决策
E 反应型       ~10      2-4     短(即时)     中             低       启发式规则
──────────────────────────────────────────────────────────────────
合计           ~200+
```

### 3.4 核心洞察

**六朝 AI 不能靠一种方法解决所有决策**，因为决策类型之间差异太大：

- **A 类（资源分配）**是搜索最擅长的：形式化、可模拟、短视界 → Beam Search
- **D 类（社交博弈）**是 LLM 最擅长的：ToM、非形式化、高影响 → LLM 直接决策
- **B/C 类（空间规划/DBG）**在中间地带：需要 LLM 的长期推理 + 搜索的精确计算
- **E 类（反应型）**简单到不需要复杂方案

这验证了 LLM-Hybrid + Beam Search 的混合架构——不是因为一种方法不够好，而是**不同决策的内在特性从根本上适合不同的算法**。

## 五、L1 对局 Agent — 三种路线

### 3.0 决策层次定义

六朝的决策自然分为两层时间尺度：

| 层次 | 频率 | 决策内容 | 分支因子 |
|------|------|---------|---------|
| **战略层** | 每回合 1 次 | 本回合优先方向：军事/文化/牌组/防守 | ~4-6 |
| **战术层** | 每步 1 次 | 具体行动选择：CourtAction? March? PlayCard? | ~15-30 |

---

### 3.1 L1-T1: HeuristicAI 增强（参考价值有限）

**做法**：在现有 HeuristicAI 基础上调优权重、增加规则。

**评价**：作为 baseline 和战术执行器有价值，但决策质量天花板低——无法发现"当前军力不足但打出谢玄后可进军"这种跨步组合。

**适用**：快速对局测试、MCTS rollout 策略、LLM-Hybrid 的执行层。

---

### 3.2 L1-T2: MCTS 搜索

#### 3.2.1 核心思路

使用 IS-MCTS（信息集蒙特卡洛树搜索）在每步行动上搜索最优决策。

#### 3.2.2 必须采用分层架构

全搜索不可行的原因：

```
单步全 MCTS:
  分支 ~20 × 深度 ~7 = 20^7 ≈ 13 亿叶子
  × 2000 rollout × 0.2s = 200s/步  ← 不可行
```

**方案：Hierarchical MCTS**

```
┌─────────────────────────────────────────────┐
│  L2 战略层 (每回合 1 次)                      │
│  ├── 搜索空间: "军事扩张"/"文化推进"/"牌组构筑" │
│  ├── 分支因子: ~4-6                          │
│  ├── 搜索深度: 剩余回合数 (~5-8)              │
│  ├── 节点数: ~6^5 ≈ 7776                     │
│  └── 叶节点评估: HeuristicAI 滚完整回合       │
│                                              │
│  L1 战术层 (每步 1 次)                        │
│  ├── 搜索空间: 当前回合内的行动序列            │
│  ├── 分支因子: ~20                           │
│  ├── 搜索深度: ~7 个行动                      │
│  ├── 节点数: MCTS ~2000 iterations           │
│  ├── 叶节点评估: 价值网络 或 手工评估函数      │
│  └── 约束: L2 选定的战略方向限制行动权重       │
└─────────────────────────────────────────────┘
```

#### 3.2.3 四大挑战

| 挑战 | 问题 | 缓解方案 |
|------|------|---------|
| **多人博弈** | 标准 MCTS 假设二人零和 | 退化单 Agent：只对当前玩家 MCTS，对手用 HeuristicAI 预测 |
| **不完全信息** | 对手手牌、牌库顺序 | Determinization：每次迭代随机采样一个"世界状态" |
| **评估函数** | 不能搜索到终局，必须在中间节点评估 | 7 维度手工函数 或 自对弈训练价值网络 |
| **Rollout 偏差** | HeuristicAI 行为 ≠ 真实玩家 → 偏差传导 | 缩短 rollout + 加深树搜索 + 校准评估函数 |

#### 3.2.4 评估函数设计（MCTS 专用）

```
Eval(s) = w1 × VP_current
        + w2 × VP_expected_final（区域控制 × 区控 VP + 文化排名预期）
        + w3 × area_control_score
        + w4 × culture_rank_score
        + w5 × deck_quality_score（流民比例/平均效果值）
        + w6 × army_progress_score
        + w7 × sima_share_score（威望/功绩 → 司马家 VP 分配）
```

#### 3.2.5 计算估算

| 场景 | 迭代 | 时间 | 可接受？ |
|------|------|------|---------|
| 每步战术 MCTS（Python，手工评估函数） | 2000 | ~2s/步 | ✅ |
| 每回合战略 MCTS | 1000 | ~1s/回合 | ✅ |
| 整局总 MCTS 时间 | — | ~200步×2s + 10回合×1s ≈ 410s | ✅ 非实时游戏 |

#### 3.2.6 路线优劣

```
优势:
  ✓ 形式化保证（足够迭代下 UCT 收敛到最优）
  ✓ 纯本地，不需要 LLM API
  ✓ 可批量并行跑（一晚上数千局自对弈）
  ✓ 搜索中自然发现战术组合

劣势:
  ✗ 局面评估函数极难设计（7+ 维度 × 非线性交互）
  ✗ 多人 Max^n 搜索效率低
  ✗ Rollout 策略偏差传导
  ✗ 需要海量自对弈训练（如果用价值网络）
  ✗ 规则改动后整个评估函数需重新训练
  ✗ 无法解释"为什么选这个行动"（对 L2/L3 不友好）
  ✗ 共享牌库的 determinization 噪声大
```

### 3.3 L1-T3: LLM-Hybrid

#### 3.3.1 核心设计理念

来自 EnvGen 洞察：**LLM 离执行层越远、离战略设计层越近，效果越好、成本越低。**

```
SPRING (Crafter):  LLM 每步选动作 → 2700 次/局 → $270/局 → ❌
LLM-Hybrid (六朝): LLM 每回合定战略 → ~15 次/局 → ~$0.10-0.50/局 → ✅
```

#### 3.3.2 架构

#### 3.3.5 路线优劣

```
优势:
  ✓ 战略层面推理能力强（理解局势、识别威胁、长期规划）

  ✓ 规则变更友好（LLM 读新规则书即可，无需重训练）

  ✗ 有延迟（每回合等待 LLM API ~2-5s）
  ✗ 无法批量并行跑数百局（API rate limit）
```

## 六、子问题：朝堂选牌

### 6.1 朝堂机制概述

朝堂选牌（CourtAction）的特点：

- **效果即时兑现**：激活卡片后立即获得资源（军力/VP/摸牌等），无延迟回报
- **每回合 1 次免费**：与进军/征募/打手牌在同一个行动循环中竞争
- **阵营牌库已知**：10 张固定组成 + 已打出的玩家策略牌，内容透明
- **决策结构**：Card A vs Card B vs "先做其他行动"

### 6.2 方案 A：纯启发式打分

**做法**：Heuristic Executor 对每个 CourtAction 给定一个分数，选最高的。

```
CourtAction(清谈)  → score = +4.2  （+6 VP）
CourtAction(士卒)  → score = +2.1  （+3 军力）
→ 选清谈
```

**局限**：看不到后续连锁。"选士卒 → +3 军力 → 进军寿春 → 占领"这条 2-3 步的组合链无法被单步打分发现。

### 6.3 方案 B：MCTS

**做法**：在朝堂选牌决策点上跑 IS-MCTS。

**模拟终点**：当前玩家回合结束（~5-15 步）

**问题**：
- 当前回合内只有自己行动，没有对手互动
- 无对抗 = 不需要 UCB 探索-利用平衡
- MCTS 的随机探索在短确定视界中是浪费迭代
- 同样局面两次决策可能不同（不稳定性）

**结论**：MCTS 是合适的算法用在了不合适的子问题上。

### 6.4 方案 C：Determinized Beam Search ⭐ 推荐

#### 6.4.1 为什么更合适

朝堂选牌退化为**带随机性的单玩家短视界规划**：

- 无对手互动（只模拟自己回合）
- 确定性环境（determinization 后牌库顺序固定）
- 短视界（5-15 步）

Beam Search 在确定性单玩家规划中优于 MCTS：更快、更准、更稳。

#### 6.4.2 算法流程

```
对每次 determinization:
  1. 随机固定牌库顺序
  2. Beam Search (K=5-10) 在确定世界上找最优行动序列
  3. 记录最优序列的根行动和得分

统计 20 次 determinization:
  → 哪个根行动被选为最优的次数最多
  → 选它
```

#### 6.4.3 伪代码

```python
def determinized_beam_search_court(state, player_id,
                                    beam_width=10,
                                    num_determinizations=20,
                                    max_depth=20):
    """朝堂选牌: Determinized Beam Search"""
    
    action_wins = defaultdict(int)      # 根行动 → 获胜次数
    action_scores = defaultdict(list)   # 根行动 → 各次得分
    
    for d in range(num_determinizations):
        # Step 1: Determinize
        world = copy.deepcopy(state)
        rng.shuffle(world.main_deck)
        rng.shuffle(world.national_deck)
        
        # Step 2: Beam Search
        best_seq, best_score = beam_search(
            world, player_id,
            beam_width=beam_width,
            max_depth=max_depth
        )
        
        # Step 3: 统计
        if best_seq:
            root = best_seq[0]
            action_wins[root] += 1
            action_scores[root].append(best_score)
    
    # Step 4: 决策 — 选"获胜"次数最多的根行动
    best_action = max(action_wins, key=lambda a: 
        (action_wins[a], np.mean(action_scores[a])))
    return best_action


def beam_search(world, player_id, beam_width=10, max_depth=20):
    """单玩家确定性 Beam Search"""
    
    beam = [(world, [], evaluate(world, player_id))]
    
    for depth in range(max_depth):
        candidates = []
        
        for state, actions, _ in beam:
            legal = get_available_actions(state, player_id)
            
            if not legal:
                # 玩家选择结束回合 → 终局评估
                candidates.append((
                    state, actions,
                    evaluate_turn_end(state, player_id)
                ))
                continue
            
            for action in legal:
                new_state = copy.deepcopy(state)
                apply_action(new_state, action, player_id)
                
                score = evaluate(new_state, player_id)
                candidates.append((
                    new_state, actions + [action], score
                ))
        
        if not candidates:
            break
        
        candidates.sort(key=lambda x: x[2], reverse=True)
        beam = candidates[:beam_width]
        
        # 如果 top 候选全是终止态，停止
        if all(is_turn_end(c[0], player_id) for c in beam[:3]):
            beam = candidates[:1]  # 只保留最优
            break
    
    best = beam[0]
    return best[1], best[2]  # (action_sequence, score)


def evaluate(world, player_id):
    """中间状态启发式评估 — 手工规则，零训练"""
    p = world.get_player(player_id)
    return (
        p.vp * 1.0
        + p.military * 1.5
        + area_control_value(p, world) * 0.8
        + hand_quality(p) * 2.0
        + deck_quality(p) * 2.0
        + culture_rank_value(p, world) * 1.5
    )


def evaluate_turn_end(world, player_id):
    """回合结束时的终局评估 — 比中间评估更完整"""
    base = evaluate(world, player_id)
    p = world.get_player(player_id)
    
    # 回合结束特有: 未激活朝堂牌的结算价值
    unplayed_court = sum(
        c.resource_vp for c in world.get_court(p.faction)
    )
    faction_share = 1.0 if p.faction == 'north' else 1.0 / 3
    base += unplayed_court * faction_share
    
    return base
```

#### 6.4.4 参数与计算量

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| beam_width | 5-10 | 太小错过好路径，太大浪费计算 |
| max_depth | 15-20 | 一回合不可能超过 20 步 |
| num_determinizations | 15-25 | 牌库顺序的随机性需要足够采样 |

| 指标 | 数值 |
|------|------|
| 单次 Beam Search 评估次数 | ~750（K=5×深度15×分支10） |
| 单次耗时 | ~0.5s |
| 20 次 determinization | ~10s |
| 每局总耗时（10 次朝堂选牌） | ~100s |

#### 6.4.5 不需要训练

Beam Search 是纯搜索算法。三个可调参数（beam_width, num_determinizations, 评估函数权重）全部手工设定。

## 七、处理未知抽牌：Determinization

### 5.1 六朝牌库系统的特殊性

```
公共牌库 (main_deck)    → 4 玩家共享 → 你的抽牌影响所有人的抽牌
强制事件牌              → 抽到即触发 → 改变模拟路径
弃牌堆重洗              → 中局发生   → 再次随机化
阵营牌库 (national_deck) → 10 张已知 → determinization 噪声小
```

### 5.2 三层处理策略

| 层次 | 处理方法 | 原因 |
|------|---------|------|
| **战略层 (LLM)** | 不 determinize，用期望值 | 只需要"牌堆还剩 ~40 张，策略牌约 12 张"这个粒度 |
| **战术层 (Executor)** | 不 determinize，用概率加权 | 对"打出谢玄后下回合抽到募兵的概率"用期望值计算 |
| **局部搜索 (Beam Search)** | Root determinization，一次迭代内固定 | 10 张已知的阵营牌库 × 有限公共牌库抽牌，噪声可控 |

### 5.3 为什么不全搜索用 Determinization

公共牌库的 determinization 噪声太大：

```
全搜索: 200 步 × 2000 迭代 × 4 玩家抽牌 × 强制事件打断
  → 一次"坏洗牌"偏差贯穿整个搜索 → 收敛极慢
```

只在**阵营牌库（已知 10 张）** 和 **本回合内少量公共牌库抽牌** 的范围内做 determinization，噪声才可控。

## 九、推荐架构

### 9.1 总体方案：LLM-Hybrid 为主 + 局部搜索增强

```
┌─────────────────────────────────────────────────┐
│                推荐的混合架构                      │
│                                                  │
│  战略层 (LLM, ~15 次/局)                          │
│  ├── 每回合 1 次: 定战略方向 → StrategicDirective  │
│  ├── 关键决策点: 僭越、终局触发、计划被打乱        │
│  └── 输出: reasoning + 结构化指令                 │
│                                                  │
│  战术层 (Heuristic Executor, ~180 次/局)           │
│  ├── 常规行动: 按战略方向加权评分                  │
│  └── 朝堂选牌: Determinized Beam Search           │
│                                                  │
│  元层 (L2/L3 共享)                                │
│  ├── LLM 的 reasoning 文本 → L2 经验总结素材        │
│  └── 跨局战略模式 → L3 平衡分析素材                │
└─────────────────────────────────────────────────┘
```

### 9.2 实现优先级

| 优先级 | 模块 | 理由 |
|--------|------|------|
| **P0** | StateEncoder（Viewport → Markdown） | 一切 LLM 调用的前提；已有 Viewport，只需加渲染器 |
| **P1** | StrategicDirective schema + 校验层 | 保证 LLM 输出合法可执行 |
| **P1** | Heuristic Executor（支持动态权重） | 战术执行层，Beam Search 的评估函数也复用它 |
| **P2** | LLM-Hybrid Agent 主循环 | 整合 P0+P1，形成可对局的完整 Agent |
| **P2** | Determinized Beam Search（朝堂选牌） | 单回合搜索增强战术精度 |
| **P2** | 关键决策点 LLM 微调用 | 僭越、终局触发、计划被打乱 |
| **P3** | L2 Post-Game Analyzer | 消费 LLM reasoning 文本 |
| **P3** | L3 Cross-Game Analyzer | 跨局统计与平衡建议 |

### 9.3 不做的事

- **不做完整 MCTS Agent**：搜索空间太大 + 共享牌库 determinization 噪声太高。仅局部使用 Beam Search
- **不做 HeuristicAI 增强为主力**：天花板太低。仅作为 Executor 基底和快速 baseline
- **不做纯 LLM Agent（SPRING 模式）**：$270/局 成本过高且效果不如 Hybrid
